# Render Deployment Guide

This guide deploys MerchPress with the Blueprint at the repository root:

```text
Browser
  │ HTTPS
  ▼
printora-web (Next.js, Render web service)
  ├─ /            ─▶ Next.js pages
  ├─ /api/*       ─▶ printora-api:10000 (private network)
  └─ /media/*     ─▶ printora-api:10000 (private network)
                         │
                         ├─ printora-db (Render PostgreSQL)
                         └─ /var/data (persistent disk for media)
```

There is no Redis or Celery worker in this topology. Exports run inline because
`CELERY_TASK_ALWAYS_EAGER=true`. Add Redis and a worker later if export volume
requires it.

## Prerequisites

- A Render account and a paid service plan. Persistent disks and
  `preDeployCommand` are not available on free web services.
- The repository pushed to GitHub with `render.yaml` at the root.
- A strong admin password and a long random `DJANGO_SECRET_KEY`. The Blueprint
  generates the secret automatically.
- The Deepseek key that was previously committed to `.env.example` must be
  rotated before this deployment is public.

## Create the Blueprint

1. Push the deployment commit to `main`.
2. In the Render Dashboard, choose **New → Blueprint**.
3. Connect the GitHub repository and select the `main` branch.
4. Render prompts for the `sync: false` values:
   - `DJANGO_ADMIN_EMAIL` — the production admin login.
   - `DJANGO_ADMIN_PASSWORD` — a unique, strong password.
5. Apply the Blueprint.

Render creates:

| Resource | Purpose |
| --- | --- |
| `printora-db` | PostgreSQL 16 |
| `printora-api` | Django + Gunicorn, media disk at `/var/data` |
| `printora-web` | Next.js storefront and API/media proxy |

The public URLs are normally:

- Storefront: `https://printora-web.onrender.com`
- API/admin: `https://printora-api.onrender.com`

If any of those names are already used in the workspace, rename the resources
in `render.yaml` and update all URLs and hostnames that reference them.

## Deploy sequence

On the first deploy Render runs:

1. Backend build: install Python dependencies and `collectstatic`.
2. Backend pre-deploy: `python manage.py migrate --noinput`.
3. Backend start: Gunicorn on `$PORT`.
4. Backend health check: `GET /api/health/` (checks the database).
5. Frontend build: `npm ci --include=dev && npm run build`.
6. Frontend start: `next start` on `$PORT`.
7. Initial deploy hook: `python manage.py seed_if_empty`.

`seed_if_empty` only runs when the product table is empty. It creates the demo
catalog (six products, mockups, templates, cliparts, fonts) and the admin user
from `DJANGO_ADMIN_EMAIL` / `DJANGO_ADMIN_PASSWORD`. It does **not** create the
demo customer or demo order. If the database already contains products, the
hook skips seeding.

The seeded store has `StoreConfiguration.demo_mode=True`. Checkout is a demo
flow until Stripe is configured and demo mode is turned off in the admin.

## Environment variables

### Backend (`printora-api`)

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | From `printora-db.connectionString` |
| `DJANGO_SECRET_KEY` | Generated by Render; never the default |
| `DJANGO_DEBUG` | `false` |
| `DJANGO_ALLOWED_HOSTS` | `.onrender.com,printora-api,printora-web,localhost,127.0.0.1` |
| `DJANGO_MEDIA_ROOT` | `/var/data/media` |
| `DJANGO_SERVE_MEDIA` | `true` |
| `SITE_URL` | Public storefront URL |
| `BACKEND_URL` | Public backend URL |
| `CORS_ALLOWED_ORIGINS` | Exact storefront origin(s) |
| `CELERY_TASK_ALWAYS_EAGER` | `true` (no worker in this topology) |

### Frontend (`printora-web`)

| Variable | Value |
| --- | --- |
| `NEXT_PUBLIC_BACKEND_ORIGIN` | `http://printora-api:10000` |
| `BACKEND_INTERNAL_URL` | `http://printora-api:10000` |
| `NEXT_PUBLIC_API_URL` | `/api` |
| `NEXT_PUBLIC_SITE_URL` | Public storefront URL |

`NEXT_PUBLIC_BACKEND_ORIGIN` is baked into the Next.js build. Redeploy the
frontend after changing it. It intentionally uses Render's private network
hostname, not the public backend URL.

## Custom domains

When adding a custom storefront domain, update **all** of these before the DNS
switch:

```text
# printora-web
NEXT_PUBLIC_SITE_URL=https://shop.example.com
SITE_URL=https://shop.example.com

# printora-api
CORS_ALLOWED_ORIGINS=https://shop.example.com
SITE_URL=https://shop.example.com
DJANGO_ALLOWED_HOSTS=.onrender.com,printora-api,printora-web,shop.example.com
```

If the backend also gets a custom domain (for example `api.example.com`), add
that hostname to `DJANGO_ALLOWED_HOSTS` and set `BACKEND_URL` to its HTTPS URL.
Render health checks send the custom domain as the `Host` header, so omitting it
causes health-check 400s and failed deploys.

Redeploy the frontend after changing `NEXT_PUBLIC_SITE_URL` or
`NEXT_PUBLIC_BACKEND_ORIGIN`.

## Media and persistence

- Uploaded designs, product mockups, design previews, clipart, fonts and
  production exports live under `/var/data/media`.
- The disk survives redeploys but is attached to one service instance. Do not
  scale `printora-api` to multiple instances while using a local disk.
- Back up both PostgreSQL and the media disk. Render's database backups depend
  on the database plan; test a restore before relying on it. Archive media with
  a one-off job or shell command, for example:
  `tar czf /tmp/media-backup.tgz -C /var/data media`.
- For multi-instance scaling, move media to S3-compatible object storage and
  update `STORAGES` plus `DJANGO_MEDIA_ROOT`-dependent code.

## Data migration from the local environment

The repository does not contain the current local catalog or media. The default
first deploy creates the six-product demo catalog. To use the local catalog:

1. Take a PostgreSQL dump from the local database.
2. Restore it into `printora-db` using its external connection string.
3. Copy the local `backend/media` contents to `/var/data/media`.
4. Redeploy or restart `printora-api`.

Because `seed_if_empty` runs automatically on the first deploy, restore a
non-empty database before the first deploy if you do not want the demo catalog,
or remove the demo products after restoring. Media files are not stored in Git.

The ad-hoc scripts in `backend/` (`seed_products.py`, `seed_plain_images.py`,
`seed_real_products.py`, etc.) can generate additional demo products, but they
are not part of the production migration path.

## Payments, email and background jobs

- **Payments:** Stripe is optional and disabled by default. Checkout remains in
  demo mode until `STRIPE_ENABLED`, `STRIPE_SECRET_KEY` and
  `STRIPE_WEBHOOK_SECRET` are configured and `demo_mode` is turned off in the
  admin.
- **Email:** no outbound email provider is configured. Password resets and
  notifications require an email service.
- **Exports:** generated inline by the web process. Long exports can tie up a
  Gunicorn thread; add a Celery worker and Redis for heavier traffic.
- **AI assistant:** uses the built-in FAQ knowledge base unless `AI_PROVIDER`,
  `AI_API_KEY`, `AI_BASE_URL` and `AI_MODEL` are configured.

## Build-time data fetching

The catalog pages do not need the backend during the frontend build. The shop,
templates and product routes render dynamically at request time and reach the
backend through Render's private network. The build only needs the
`NEXT_PUBLIC_*` values, which are baked into the client bundle and the rewrites.

## Verification checklist

After the first deploy:

- [ ] `https://printora-api.onrender.com/api/health/` returns
      `{"status":"ok","service":"printora-api","database":"ok"}`.
- [ ] `https://printora-web.onrender.com/` loads.
- [ ] `/shop` lists the seeded products.
- [ ] `/media/...` images load through the storefront.
- [ ] Admin login works at `https://printora-api.onrender.com/admin/`.
- [ ] Register, login, add to cart, checkout (demo), and export work.
- [ ] Changing `DJANGO_ADMIN_PASSWORD` after the first deploy does not change
      the existing admin password; update it in the admin instead.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `DisallowedHost` / 400 | Custom domain missing from `DJANGO_ALLOWED_HOSTS`. |
| CSRF 403 after login | Storefront origin missing from `CORS_ALLOWED_ORIGINS`; redeploy backend. |
| Health check 503 | Database unreachable or migrations failed; inspect pre-deploy logs. |
| Media 404 after redeploy | Disk not mounted at `/var/data` or `DJANGO_MEDIA_ROOT` changed. |
| Admin CSS missing | `collectstatic` failed or WhiteNoise has no `staticfiles` directory. |
| Frontend build cannot reach backend | Expected; build-time fetch is best-effort. Verify runtime proxy. |
| `next start` exits immediately | `NEXT_PUBLIC_*` values changed after build; redeploy the frontend. |
| API 403 from browser | `CORS_ALLOWED_ORIGINS` does not exactly match the browser origin. |
| Empty catalog after first deploy | Initial hook failed or was skipped; run `python manage.py seed_if_empty` in the Render Shell, or import your catalog. |

## Security follow-up

- Rotate the Deepseek API key that appeared in `backend/.env.example`. Removing
  it from the current tree does not remove it from Git history.
- If history rewriting is required, use a coordinated `git filter-repo` run and
  force-push only after all collaborators are notified.
- Keep `DJANGO_DEBUG=false`; the settings module refuses to start in production
  with the default secret.
- Do not enable `DJANGO_SSL_REDIRECT` while the frontend proxies API and media
  over Render's private HTTP network. Render terminates TLS at its edge.
- `python manage.py check --deploy` reports one expected warning
  (`security.W008`) for the redirect setting; HTTPS is enforced by Render.
